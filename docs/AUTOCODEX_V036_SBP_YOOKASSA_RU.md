# Autocodex v0.36.0 — безопасные платежи СБП и сверка возвратов YooKassa

**Базовая версия: v0.35.0.** Это инкрементальный ZIP, не полная замена проекта. Пакет не содержит `.env`, секретов, `node_modules` или БД. Никаких новых Alembic-миграций в этом выпуске нет.

## Что реально изменено

1. **Read-only сверка возвратов:** `payments/refund_reconciliation.py` создаёт уникальные задания `refund_reconcile:{refund_uuid}` для возвратов с известным внешним ID в статусах `provider_pending`/`uncertain`. Каждое задание выполняет только `GET /v3/refunds/{id}`. Оно никогда не отправляет повторный `POST /refunds`, даже после сбоя, повтора задания или истечения 24-часового окна идемпотентности YooKassa.
2. **Строгая сверка:** внешний ID возврата, связанный ID платежа, сумма `Decimal` с точностью до копейки, явная валюта `RUB` и допустимый статус должны совпадать. Неизвестная валюта, повреждённый ответ или несовпадение данных переводят задачу в `manual_review`. Подтверждённые состояния не регрессируют в `pending`.
3. **Отказоустойчивость:** максимум 12 опросов с ограниченным экспоненциальным интервалом (1–240 минут), без бесконечного polling. Зависшие `running` задания проверки платежа или возврата допускается восстановить **только для безопасной операции GET**. Запросы создания/возврата денег и закупки не перезапускаются автоматически.
4. **Первичный ответ на POST возврата:** если ответ банка не содержит корректного ID платежа, ID возврата, суммы, RUB и состояния, локальная запись остаётся `uncertain`, повторная отправка запрещена до ручной банковской сверки.
5. **API админа:** существующий `/api/v1/payments/admin/refunds/{uuid}/reconcile` использует тот же проверенный read-only код. Очередь `/api/v1/payments/admin/refunds/needs-reconciliation` показывает состояние фонового задания и флаг ручной проверки, без сумм/личных данных.
6. **Проверка целостности оплаты:** `verify_remote()` по-прежнему требует авторитетный GET статуса YooKassa, `payment_method=sbp`, идентичность заказа и RUB, а теперь перед созданием закупочной задачи проверяет сумму позиций `OrderLine` против общей суммы заказа. Неверные данные — HTTP 409 без перехода к исполнению.
7. **Безопасность HTTP-клиента:** внешние provider ID не могут быть частью URL-пути/параметров произвольного формата, ключи идемпотентности ограничены 64 символами. Добавлена имитация перехода возврата в окончательный статус в `FakeYooKassa` для dev/CI.
8. **Версионирование:** `pyproject.toml` и запасной `app/main.py` обновлены до `0.36.0`.

## Что принципиально НЕ включено

- Боевой `/api/v1/checkout` в `app_env != test` **по-прежнему возвращает 503**. Не принимать реальные СБП-оплаты до подписанных контрактов закупок, фискального сценария и приёмки. Никакие флаги закупок не изменены.
- Планировщик **отключён по умолчанию**: `PAYMENTS_RECONCILIATION_ENABLED=false`. После тестирования в песочнице допускается включить существующий параметр `true`; при этом выполняются только банковские GET-проверки, без автоматического инициирования оплат или возвратов.
- Для созданного возврата с потерянным внешним ID автоматической безопасной сверки нет: требуется сверка с банковским кабинетом и поддержкой. **Не повторять POST с новым ключом**.
- Нет автоматического бухгалтерского закрытия, финального фискального контроля чеков возврата и внешнего подтверждения закупок ADEO/PARTKOM/Forum. Жизненный цикл v0.35 остаётся неполным.
- Автоматическая обработка `refund.*` webhook не добавлена: провайдерный GET и админская сверка не требуют доверия к неаутентифицированному входящему уведомлению. Нельзя придумывать HMAC по secretKey для уведомлений API v3.

## YooKassa: важные контрактные ограничения

- `Idempotence-Key` действует в YooKassa **24 часа**. После этого тот же POST может выполниться повторно. Поэтому при неопределённом результате возврата и оплат **никаких автоматических повторов POST не предусмотрено**.
- Для исходящих `/payments` и `/refunds` используются `Idempotence-Key` и рубли; для подтверждения денежных операций — авторитетный `GET` и совпадение идентификаторов, валюты и суммы.
- Приём webhook в production должен быть дополнительно защищён на границе сети/доверенного прокси проверкой опубликованных IP YooKassa, но эти доверенные IP/инфраструктура в этом архиве не настроены.
- Проверить режим фискализации и создание чека возврата по действующему договору и НДС; здесь система этого не подтверждает.

## Испытания

- Автономные тесты не обращаются к реальному банку или поставщикам (см. `tests/conftest.py`).
- Проверены: строгий RUB, idempotency, read-only polling, статусы pending/succeeded/manual_review, отсутствие двойной отправки возврата, API администратора, ограничение внешних ID, проверка суммы строк перед исполнением.
- Полный pytest-тестовый набор **не объявляется пройденным**: локальный Python 3.13 не совпадает с требуемым Python 3.14 и у него отсутствует драйвер `psycopg`. База пользователя PostgreSQL 18.6 не доступна в этой среде. Перед релизом обязательны Docker-проверки.

## Установка / проверки — PowerShell, строго одна физическая строка

Архив скопировать в `Downloads` и применять **только поверх v0.35.0** с проверкой `V036_MANIFEST.json` (команда при выдаче файла в чате). Не нужно делать `git apply`.

После применения ZIP:

`Set-Location 'C:\Users\bogdan\Desktop\autocodex'; docker compose up -d --build; docker compose ps`

Логи:

`Set-Location 'C:\Users\bogdan\Desktop\autocodex'; docker compose logs --tail=100 migrate web worker`

Тесты в контейнере при наличии dev-зависимостей:

`Set-Location 'C:\Users\bogdan\Desktop\autocodex'; docker compose exec web python -m pytest -q tests/test_sbp_payment_refund_v036.py`

Не включать платежи/отправку закупок только на основании успешного `docker compose up`: необходима проверка на тестовом магазине YooKassa и подтверждение работоспособности всех закупочных API.
