# Autocodex: точечный аудит и hardening v0.33.3

## Исходная база и порядок изменений

Исходник — присланный `autocodex(8).zip` (v0.33.2). Полный код доступен; исправления сравнены с файлами **самого исходного ZIP**, не с `git HEAD`, поскольку проект уже содержит незакоммиченные пользовательские изменения. Исходный ZIP не перезаписан.

Порядок: **G1 → A/B/C/D → E/F → G2–G5**. В этот пакет включены только подтверждённые точечные исправления с автономными тестами. Модули автоматической закупки и основные схемы БД намеренно не заменялись непроверенными реализациями.

## Файлы и архитектура

- G1: `app/modules/marketplace/checkout_v017.py`, `cart.py`; `app/modules/supplier_feeds/parsers.py`.
- A/B/C/D: `app/modules/offer_engine/providers.py`, добавлены `supplier_errors.py`, `currency.py`, `resilience.py`, `soap_client.py`, `secret_redaction.py`; старые `suppliers/adapters/{__init__,base,rossko}.py` превращены в совместимые фасады, чтобы устранить отдельную заглушку; единый живой реестр read-адаптеров остаётся в `offer_engine.providers`.
- F: `app/modules/payments/gateway.py`, `api.py`, `app/core/config.py`; добавлен отключённый по умолчанию тестовый шлюз `FakeYooKassa`.

- Регрессии: новый `tests/test_hardening_v0333.py` и согласованные изменения существующих тестов (`test_supplier_feeds.py`, `test_finance_f2.py`, `test_rossko_real_getsearch_v0143.py`, `test_unit.py`, `test_commerce_flow.py`).

## Реализовано и проверено

### G1

1. Проверка workflow в v0.17 исправлена на `!= 'v017'`. Тест HTTP-роута подтверждает 404 для заказа другого workflow.
2. Разбор количества: нулевой остаток допустим; ноль для `minimum` и `multiple` запрещён; строка `1.0` принимается только если это математически целое число. Поддержан числовой Python `0` для остатка.
3. В CSV PART-KOM поле `Мин.Партия` означает `minimum`; **колонки кратности упаковки в принятом CSV нет**. В отсутствие источника `multiple=1` (не подмена `minimum`). Настоящую кратность требуется подтвердить через контракт поставщика.
4. Корзина больше не вызывает исключение на пустом или невалидном списке вариантов остатков. Операция записи использует существующую синхронизацию на уровне пользователя; полная атомарность между внешней ценой поставщика и заказом **не доказана**.
5. Публикация нулевых остатков уже отсеивается существующим условием `FeedOffer.stock_min > 0` в витрине; нулевой остаток сохранён в фидах для корректного учёта.

### A/B/C/D — read-интеграции поставщиков

- Одна активная registry/factory для поиска предложений; совместимые старые пути делегируют активному коду.
- Типизированные ошибки: `NetworkError`, `UpstreamBusinessError`, `MalformedResponseError`, `UnsupportedCurrencyError`, а также `Unavailable` для совместимости.
- Для идемпотентных запросов: до 3 попыток, экспоненциальная задержка с jitter, общий таймаут, per-provider breaker и half-open probe; 408/429/5xx считаются временными, 4xx — бизнес-ошибкой.
- `require_rub()` применяется ко всем четырём парсерам API; денежные значения декодируются как Decimal/нормализуются до копеек. Пустая/неизвестная валюта **блокирует** предложение.
- HTTP transport и парсинг разделены на уровне отдельных функций для важных форматов; полная выделенная транспортная реализация каждого провайдера остаётся задачей следующего этапа.
- WSDL ROSSKO кэшируется на event-loop и версию URL; закрывается при завершении приложения.
- Добавлены фильтры удаления секретов из логов; они не заменяют запрета логирования HTTP-тел и настроек сервера/прокси.

**Критическая эксплуатационная несовместимость:** фактические примеры ROSSKO в архиве не содержат подтверждаемого поля валюты. Строгий RUB-only парсер теперь **обоснованно откажет** при получении таких ответов. Перед включением проверить официальные контракты ROSSKO, PART-KOM, Forum, ADEO и указать достоверный источник RUB; если контракт гарантирует RUB вне тела ответа, фиксировать именно этот источник и тесты, а не молча подставлять RUB. С текущим guard нельзя заявлять работоспособность живого поиска по всем API.

### F — YooKassa

- Действующий `SELECT ... FOR UPDATE` платежей и сверка состояния по API провайдера сохранены; HTTP-вебхук валидирует структуру события и выполняет независимый GET статуса.
- Унифицированы Decimal-проверки суммы и позиций чека, запрещены бинарные float, строго проверяется совпадение итогов чека и суммы оплаты.
- В памяти реализован fake с идемпотентностью по ключу и управляемой проверкой успешности; выбирается только в `app_env=test` при `yookassa_fake_enabled=true`.
- **HMAC на основе YooKassa secretKey НЕ реализован:** официальный YooKassa API v3 не задаёт такого HMAC-контракта для webhook. Правильный путь — сверка подлинного статуса GET `/payments/{id}` и ограничение адресов отправителя на ingress с корректной настройкой доверенных прокси. Официальная документация: https://yookassa.ru/developers/using-api/webhooks .
- Автоматический периодический reconciliation-job для всех неопределённых платежей в данном пакете не добавлен; есть ручные механизмы refresh/reconcile. Отдельно требуется расписание и idempotent DB queue.

### G2–G5

- Расчёт `MARKUP_SIMULATION` учитывает последнюю милю в базе наценки; перебор SMART_UP переработан; добавлены консервативные пределы процента наценки/комиссии для предварительных F2-симуляций. **Это не разрешение менять боевую цену checkout без утверждённой политики.**
- Публичные дорогие GET при недоступном Redis переключаются на ограниченный in-process лимитер; write/auth/webhook остаются fail-closed. Мультиинстансную защиту обязан обеспечивать ingress.
- Ограничение HTTP тела учитывает chunked/streaming; тест HTTP возвращает 413.
- Обработка очереди фидов ограничена по времени ожидания и нецикличным завершением; worker ограничивает безопасные ретраи зависших задач и эскалирует на ручную проверку. Внешние операции с возможным сайд-эффектом автоматически не повторяются.
- Нормализация email `.strip().lower()` на пути входа/создания администраторов.

## Оставшиеся пункты задания — НЕ закрыты

1. **A/E**: полный единый интерфейс `fetch_offers / check_stock / create_order / status / cancel` для каждого поставщика, подтверждение API-контрактов заказов ADEO/PARTKOM/Forum, их фактический live-submit, идемпотентный durable outbox/state machine. В проекте уже есть отдельный реальный контур закупки ROSSKO; его нельзя подменять или автоматически включать непроверенные маршруты. Самовывоз запрещён, только курьер на разрешённый адрес, контактные данные склада/ПВЗ, UUID заказа в ROSSKO `PARTS.Part.comment`.
2. **F**: фоновая сверка зависших YooKassa-платежей/возвратов, полный продакшен-тест с webhook от доверенных IP/через GET, стресс-тест параллельных callbacks.
3. **G3**: последовательное удаление промежуточных `commit()` аудита в `sale_lifecycle`/других путях, durable optimistic locking/version в закупках, полноценный SQL CAS `queued→processing` и persisted `attempts/next_run/dead_letter` для batch job. Предлагаемые изменения требуют миграций и контрактов транзакций.
4. **G5**: refresh-token rotation, формальная политика RBAC и уникальный индекс нормализованных email с миграцией дублей, `quote_workflow` контрактные пороги, доказанный debounce потока manual-review, все middleware-роуты (ограничен проверенный наиболее рискованный путь).
5. **G2**: сквозной аудит price/repricing path, лимиты из бизнес-правил, согласованное денежное Decimal-представление в *каждой* таблице/схеме и удаление всех преобразований через float за пределами изменённых модулей.

## Alembic

В **текущем патче не изменена SQLAlchemy-схема БД**: новых Alembic-миграций нет. Для завершения перечисленных durable-функций потребуются отдельные миграции: order submit/outbox/idempotency, attempts и dead-letter синхронизации, версии блокировок procurement, нормализованный email/unique key, возможно конфигурация платежных reconciliation jobs. Не выполнять `alembic upgrade` с вымышленной миграцией.

## Установка на Windows PowerShell

В каталоге существующего проекта через `git apply --check` сначала проверьте отсутствие конфликтов, затем `git apply` (сохраните локальные изменения отдельно). Все команды — одна физическая строка:

`Set-Location 'C:\Users\bogdan\Desktop\autocodex'; git apply --check 'C:\ПУТЬ\autocodex_v0333_unified.patch'`

`Set-Location 'C:\Users\bogdan\Desktop\autocodex'; git apply 'C:\ПУТЬ\autocodex_v0333_unified.patch'`

Путь `C:\ПУТЬ\...` замените на расположение скачанного патча. Если ваш код отличается от исходного архива, используйте ZIP с **только изменёнными файлами** для ручного трёхстороннего сравнения; не перезаписывайте конфликтующие файлы вслепую.

`Set-Location 'C:\Users\bogdan\Desktop\autocodex'; docker compose run --rm web uv run --group dev python -m pytest -q tests/test_hardening_v0333.py`

Для полного набора: `Set-Location 'C:\Users\bogdan\Desktop\autocodex'; docker compose run --rm web uv run --group dev python -m pytest -q`

Пакет не включает секреты, `.git`, `.env`, `.venv`, базу данных или сторонние бинарники. Это **частичная техническая поставка, не промышленный релиз полной интеграции**.
