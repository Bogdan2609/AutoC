# AutoC 0.43.0 — Operations & Observability

## Область изменения

**Версия базового проекта: 0.42.1.** Никаких новых миграций, изменённых банковских реквизитов, API-ключей и исходящих закупок. Штатные read-only контуры остаются изолированы от любых write-операций.

### Worker

- Heartbeat в отдельной SQLAlchemy-сессии каждые 20 секунд, с `UPDATE jobs.due_at` при совпадении `id`, `status=running`, поколения `attempts` и действующего срока.
- Поколение выполнения использует существующий монотонный `Job.attempts` вместо нового поля/миграции.
- Финальное обновление статуса допускается только владельцем текущего поколения; запрещено устаревшему исполнителю менять завершение после перехвата.
- Рестарт старых финансовых / внешних write-задач **не разрешается** без независимой сверки; уже существующая политика ручной проверки сохраняется.
- **Ограничение:** защита финального статуса не является полным fencing каждого внутреннего коммита старых handlers. До production следует добавить доменные fencing-условия в операции, которые коммитят состояние до завершения задачи, и провести много-worker PostgreSQL испытания с убийством процесса.

### API мониторинга

Администратор (`require_admin`), только чтение:

- `GET /api/v1/backoffice/operations-health/summary` — сводка очередей, платежей, возвратов, закупок.
- `GET /api/v1/backoffice/operations-health/jobs` — первые 100 текущих незавершённых/проблемных задач; никакой сериализации payload.
- `GET /api/v1/backoffice/operations-health/payments` — требующие сверки СБП-платежи.
- `GET /api/v1/backoffice/operations-health/refunds` — неопределённые возвраты.
- `GET /api/v1/backoffice/operations-health/purchases` — неопределённые попытки закупки.
- `GET /api/v1/backoffice/operations-health/supplier-factory` — список аккаунтов, флаги и количество разрешённых курьерских направлений, без секретов и адресов.

Статусы `manual_review` и `failed` различаются: первое — необходимость решения оператора, второе — ошибка обработки. Отсутствие идентификатора внешней операции никогда не означает, что внешняя операция не была исполнена.

### СБП — страница результата

- `GET /sbp/result/{order_id}` — публичная нейтральная HTML-страница после банковского redirect (`no-store`, `noindex`), **без отображения статуса, суммы и деталей заказа**; банковский redirect не несёт заголовка Bearer.
- `GET /api/v1/orders/{order_id}/sbp-result` — JSON той же read-only информации.
- Ни callback, ни пользовательский redirect не помечают платёж успешным. Сообщение об успехе выдаётся только по единственному идентифицированному `Payment.status=succeeded` с точной суммой и финальным заказом. Без внешнего идентификатора — никогда.
- Страница **не** инициирует создание нового платежа, повторное списание или самостоятельный GET в банк.

### shadcn/ui

Новая страница `/admin/system/operations`: worker, СБП, возвраты, закупки, проверенные направления API-аккаунтов. Ссылка из центра интеграций, сохранён RBAC/CSRF-контур. Интерфейс не содержит кнопок повторной отправки платежей/закупок.
