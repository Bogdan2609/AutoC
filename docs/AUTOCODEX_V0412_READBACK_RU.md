# AutoC v0.41.2 — Supplier Order Readback & Contract Verification

## Назначение

Релиз реализует **операторское чтение внешнего заказа** через подтверждённый `SupplierAccount` + `SupplierDestination` + `FulfillmentNode`.

Сверка не является основанием для `supplier_confirmed`: интерфейс показывает диагностические статусы, а изменения `Order`, `Procurement`, `SupplierPurchaseAttempt`, платежей и любых закупок **отсутствуют**.

## API

`POST /api/v1/admin/marketplace/supplier-accounts/{account_id}/order-readback`

Тело: `{"destination_id":"UUID", "external_reference":"1234567"}`. Для PARTKOM — неизменный `reference` из оформления. Для остальных — положительный числовой ID внешнего заказа. Только административный доступ, включая CSRF для staff-сессии.

Перед сетевым запросом: проверка глобального `SUPPLIER_API_ENABLED`, отдельного аккаунта, разрешённого направления, собственного активного склада/ПВЗ и наличия credentials; Redis-квота `claim_supplier_budget`. `APP_ENV=test` запрещает обращения к поставщикам.

Сеть строго только фиксированных доменов, HTTPS, без редиректов и наследования proxy env. URI и тело ошибок поставщиков в HTTP-ответ не возвращаются. Внешний HTTP POST ADEO `getOrderStatus` является документированной READ-операцией.

## Методы и ограничения

| Поставщик | Метод | ID | Осторожность |
|---|---|---|---|
| ROSSKO | SOAP v2.1 `GetOrders(order_ids.id)` | Положительный внешний id | Точечный запрос, не подбор N последних; отсутствие ответа не доказывает неотправку |
| ADEO | XML `getOrderStatus` | id заказа/строки | Отдельные статусы и частичное количество; неоднозначный `<detail>` — ручная сверка |
| PARTKOM | `GET /v4/basket/motion/{reference}` | Наша строка reference | Нет гарантии идемпотентности повторного оформления |
| FORUM-AUTO | `GET /v2/listorders?did=` | did | Статус 90 — самовывоз у поставщика, не доставка до нашего ПВЗ; 100 — выдача, но не доказательство нашего получения |

**Важно:** live-адреса, точные формы ответов, права аккаунтов и состояние курьерских маршрутов в кабинете должны быть проверены перед производственной эксплуатацией. Документы являются источником для контрактов, но не подтверждают возможности конкретного аккаунта. Каждый live-запрос требует явного действия оператора.

## Нормализация

Допустимые диагностические результаты: `found`, `not_found_in_response`, `partial`, `canceled`, `manual_review`. Любой ответ содержит `supplier_confirmed=false`, `buyer_delivery_confirmed=false`, `authoritative_proof=false`, `manual_reconciliation_required=true`.

Не возвращаются raw XML/JSON, складские/покупательские контакты, реквизиты, сообщения поставщика, URL с логином/паролем и комментарии. Денежные значения только если формально представлены Decimal/целочисленно, без float-подтверждения.

## Безопасность

- **Никаких внешних WRITE** (`GetCheckout`, `make_orders`, `basket/order`, `addGoodsToOrder`, `cancelOrder`).
- Никакой автоматической смены статусов покупки или buyer order.
- Повторный API-запрос не повторяет оформление, списание и закупку.
- Отсутствие во внешней выборке — неопределённость, не отказ поставщика.
- Курьерские направления только к собственным проверенным складам/ПВЗ, без автосамовывоза.
- Контактные данные склада/ПВЗ не включены в ответ API.

## Покрытие

Тесты на точную идентичность заказа, частичный отказ, некорректный ID, XML entity injection, redaction, Forum 90, неизвестный статус, read-only HTTP и отсутствие write-операций.

Без Alembic-миграций и без изменения `.env`. Доказательства реальной приёмки и PostgreSQL race-тесты остаются незакрытыми, поэтому `LIVE PAYMENTS / PURCHASES: NO_GO`.
