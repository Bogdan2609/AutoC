# Autocodex patch v0.33.4 — аудит RBAC и сверка СБП

## База применения

Накладной ZIP для уже установленного **autocodex_v0333_changes.zip**. Файлы в архиве расположены относительно корня проекта. Не является полной поставкой исходного репозитория; исходная структура приложения и настройки сохраняются.

## Изменения

1. `app/modules/admin_staff/route_audit.py` — отсутствующий в исходном архиве модуль проверки правил `policy.py` и защиты реальных API-маршрутов. Считывает фактические FastAPI APIRoute, обнаруживает незарегистрированные административные URI, отсутствие `Depends(require_admin)` (включая вложенные зависимости), дублирующиеся method+path. Логин, `/session` и `/logout` обрабатываются отдельными механизмами аутентификации. Поле `functional_parity_verified=False` не маскирует отсутствие UX-аудита.
2. `app/modules/payments/reconciliation.py` — периодическая **read-only** сверка созданных платежей с известным `provider_id`. Используются существующие `jobs`, ключ `payment_reconcile:<payment_uuid>`, ограниченные повторные GET-проверки, возрастающий интервал с верхним пределом 240 минут, эскалация в `manual_review` после 12 проверок. Никаких повторных вызовов `create`, `refund` или закупок.
3. `app/workers/runner.py` — создание задач сверки через worker refresh-loop и обработчик `payment_reconcile`, атомарное использование существующей очереди `jobs` и механизма claim. При выключенной опции задача откладывается, а не теряется.
4. `app/modules/payments/api.py` — при `SELECT ... FOR UPDATE` используется `populate_existing=True` для обновления Payment из БД под блокировкой. Новый защищённый `GET /api/v1/payments/admin/payments/needs-reconciliation`: показывает платежи без корректного provider ID, состояние reconciliation job и необходимость ручной проверки, **не отдавая покупательский PII/суммы**.
5. `app/core/config.py` — новый флаг `PAYMENTS_RECONCILIATION_ENABLED=false` по умолчанию.
6. `tests/test_security_reconciliation_v0334.py` — тесты для перечисленных контрактов, полностью offline.

## Включение

Настройка `PAYMENTS_RECONCILIATION_ENABLED=true` должна производиться **только после** тестирования тестового YooKassa, доступности учётной записи и мониторинга очереди. Если флаг не добавлен в `.env`, фоновые запросы к банку не выполняются.

Пример команды PowerShell **одной физической строкой** для проверки, без включения реального checkout:

`Set-Location 'C:\Users\bogdan\Desktop\autocodex'; docker compose up -d --build; docker compose ps`

Фоновые банковские запросы не отправляют деньги; работающая «реальная» закупка у ROSSKO остаётся в отдельном, защищённом и по умолчанию выключенном контуре. Ни курьерские ограничения, ни контакты склада/ПВЗ, ни UUID в ROSSKO GetCheckout **не изменялись**. Прямой live-checkout клиентов по-прежнему не включён этим патчем.

## Тесты

- 126 passed — сфокусированный регрессионный набор (админ v0.12, новый пакет, v0.33.3, работа с фидами, финансовые расчёты, checkout v0.17).
- Полный запуск с `--maxfail=1`: **301 passed, 1 failed**. Тест `tests/test_marketplace_foundation_v07.py::test_two_accounts_same_supplier_never_merge_snapshot_context` ожидал две поисковые задачи, а увидел пять (два аккаунтных и три глобальных). Тот же тест **в точности так же падает на предыдущей v0.33.3** без данного патча; отдельный дефект/изоляция теста требует разбора. При аварийном завершении теста штатный тестовый SQLite teardown также пишет исключение о закрытой БД.
- `python -m compileall -q app` пройден.
- Тесты запускались в доступном окружении Python 3.13, **а pyproject требует >=3.14,<3.15**. Для релиза необходим прогон в целевых контейнерах PostgreSQL/Redis и проверка банка в sandbox; работа YooKassa/ROSSKO на живых учётках этим аудитом не утверждается.

## Миграции

**Новых миграций Alembic нет**. Используются существующие `sbp_payments`, `jobs`. Поля и индексы этих таблиц не менялись.

## Незакрытые области

- Полный G3 (атомарный аудит в бизнес-транзакции, конкурентные закупки), A/E (проверенный live lifecycle у всех поставщиков), G5 (ротация refresh-токенов), глобальная изоляция аккаунтных и глобальных поисков.
- Строгая RUB-проверка отсутствующего поля валюты в реальных ответах ROSSKO и некоторых других поставщиков остаётся **блокирующим условием интеграции**, пока не подтверждён официальный контракт валюты.
- Для платежа с неизвестным `provider_id` после неясного POST: **только ручная сверка через кабинет банка; не повторять создание новым ключом**.
