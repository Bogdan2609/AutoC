# Autocodex v0.33.5 — защита изоляции API-аккаунтов поставщика

## База установки

**Инкрементальное обновление поверх v0.33.4, которое само устанавливается поверх v0.33.3.**
Это не полная копия проекта. Архив содержит только перечисленные изменённые и новые файлы.

## Причина предыдущего падения теста

В `test_two_accounts_same_supplier_never_merge_snapshot_context` проверка количества **всех** `Job(kind='search')` ожидала 2, хотя для этого запроса можно поставить 2 account-scoped задачи PARTKOM и 3 global задачи **других** поставщиков. Это не является доказательством утечки между двумя аккаунтами PARTKOM.

Тест теперь ограничивает выборку задач `supplier='partkom'` и проверяет, что обе имеют разные `account_id` и разные `lookup_key`, а созданные OfferSnapshot остаются обособленными по аккаунтам и цене. Другие поставщики не получают доступ к аккаунту PARTKOM.

## Действительные исправления работоспособности

1. `app/workers/runner.py`: **запрет устаревшей legacy-задачи**. Если для поставщика уже зарегистрирован хотя бы один `SupplierAccount`, запрос из ранее поставленной global/unscoped задачи не вызывает провайдер с default credentials. Указанный legacy CacheState переводится в disabled; задача завершается обычным завершением worker без обращения к API. Заблокированы в том числе случаи, когда аккаунт отключён или не имеет активного склада.
2. `app/workers/runner.py`: **проверка соответствия ключа**. Для account-scoped задачи вычисляется `account_key(brand, article, account_id, destination_id)` и проверяется на полное совпадение с payload `key` до вызова провайдера. Чужой ключ не передаётся в поставщика и чужой CacheState не изменяется.
3. `app/workers/runner.py`: **повторная проверка live-разрешений после ответа API**. После возврата из сетевого запроса проверяются актуальные `enabled/read_enabled`, `destination.enabled/verified`, активность склада и соответствие `merchant_id` аккаунта и склада. Если аккаунт или адрес был отключён во время запроса, новые снапшоты не публикуются. Это дополнительная защита; окончательную конкурентную атомарность надо проверить на PostgreSQL.
4. `tests/test_offer_engine_v03.py`: административный policy-test стал независимым от локального `.env` с настроенными API-credentials; реальные проверки secrets/config остаются в специализированных тестах.

## Тесты

- Новые тесты `tests/test_account_scope_hardening_v0335.py`: старый unscoped job после создания аккаунта; чужой cache-key в account job; отключение аккаунта во время read-only HTTP-запроса — везде контролируется отсутствие нежелательного вызова/публикации.
- Исправлен регрессионный тест в `tests/test_marketplace_foundation_v07.py`.
- Выборка из 11 тестовых файлов: **94 passed**.
- Расширенный общий запуск: **582 passed, 1 skipped**, затем падение `tests/test_unit.py::test_liveness_and_admin_denied_without_token` из-за отсутствующего в проверочной среде модуля `psycopg` (`ModuleNotFoundError`). После первой ошибки прогон остановлен (`--maxfail=1`). Исходный `pyproject.toml` требует Python `>=3.14,<3.15` и `psycopg[binary]`; используемое здесь тестовое окружение — Python 3.13. Поэтому **полный релизный прогон на целевом Docker/PostgreSQL не подтверждён**.
- Никаких запросов к реальным поставщикам/платежам в тестах нет.

## Ограничения

- Алгоритм выбора ближайших 4 направлений API и TTL кэша не изменены.
- В существующей структуре `SupplierItem` общий для supplier/external_key, а `OfferSnapshot` и `CacheState` привязаны к account + destination; полная промышленная проверка загрязнения данных под конкурентностью — отдельная задача.
- Не менялись API-контракты, курьерские маршруты, схема закупок, YooKassa и настройки валюты RUB.
- **Никаких новых Alembic-миграций.** Боевая отправка заказов у других поставщиков не включена.
- Исходный `.env`, ключи/токены и пользовательские локальные изменения **не включены** в обновление и не должны замещаться содержимым ZIP.

## Оставшаяся дорожная карта

1. **v0.34 — Адаптеры**. Единый контракт read/check/order/status/cancel, корректная валюта в каждом API, стабилизация SOAP/WSDL, тестовые фикстуры.
2. **v0.35 — Закупки**. Durable idempotency/outbox, очереди, обязательная курьерская доставка на разрешённый адрес, контакты точки приёмки, ROSSKO UUID в `PARTS.Part.comment`; безопасное подключение write API прочих поставщиков после подтверждения их контракта.
3. **v0.36 — Деньги и YooKassa**. Подтверждённый платеж СБП, двойные callbacks, reconciliation/возвраты, проверка инвариантов на PostgreSQL.
4. **v0.37 — Ценообразование**. Полный RUB/Decimal, закупка с НДС, маржинальность, last-mile, лимиты комиссий.
5. **v0.38 — Целостность и безопасность**. Транзакции, конкурентность, роли, токены, очереди, аварийное восстановление.
6. **v0.39 — Release readiness**. Миграции на Postgres, тесты API с sandbox и негативными сценариями, нагрузочные тесты, инцидентный runbook и выпуск.

Этапы — план, не гарантия фиксированного объёма: новые дефекты при интеграции могут потребовать дополнительных работ. Переход в live procurement требует отдельного контролируемого испытания; сами ZIP-пакеты не подтверждают готовность к реальным закупкам.
