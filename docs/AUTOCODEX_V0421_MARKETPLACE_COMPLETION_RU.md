# AutoC v0.42.1 — Marketplace & Data Integrity, второй интеграционный пакет

Устанавливается поверх **v0.42.0**. Следуем согласованному roadmap: 0.42 — коммерческая целостность, 0.43 — эксплуатация, 0.44 — приёмка.

## Реализация

1. `marketplace/cart.py`: собственный склад обрабатывается через 5 пакетных SQL-запросов без б/у (offers, stores, merchants, terms, balances/nodes) или 6 при наличии б/у (добавляется used); дополнительно загружаются маршруты по merchant при необходимости. Отдельные маршруты затем вычисляются по прежним торговым и логистическим правилам; supplier-backed seller offers по-прежнему идут через существующие live-quote проверки. Нет изменений резервирования/закупок.
2. `checkout_v017.py`: коммерческие варианты одного `product_id + pickup_node_id` в рамках ОДНОГО evaluate() переиспользуют read-only результаты `/offers` через ContextVar. Контекст очищается при завершении, данные нельзя переиспользовать между пользователями/ревизиями.
3. Price drift: единая проверка точной цены и тарифа в RUB; отрицательные, неверные дробные копейки, NaN, Infinity и нулевые розничные цены не проходят. Возвращаем раздельные дельты `unit_delta`, `route_delta` и требование повторного подтверждения покупателем. `grand_total`/SBP не включаются этим патчем.
4. Legacy reservations: операторский отчёт теперь сверяет исходный `InventoryMovement`, ключ освобождения, уникальность использования ключа в заказах, количество, исходный баланс. Пакет **не освобождает** сомнительные старые резервы: текущий legacy ledger не имеет отдельного per-order ownership ключа, значит автоматическое исправление остатка было бы потенциальным списанием чужого резерва. Новый v017 не создаёт reserve.
5. Snapshot retention: отдельный скрипт для **dry-run** и ручного ограниченного удаления только старых непривязанных повторных `OfferSnapshot`, имеющих более новый снимок того же item/account/destination. `OrderLine`, `CartLine`, `SupplierPurchaseAttempt` защищаются повторной проверкой, PostgreSQL FK и транзакцией; максимум 100 записей за запуск. По умолчанию ничего не удаляет. На production `--apply` заблокирован до отдельной maintenance-процедуры; необходимо резервное копирование и PostgreSQL тесты.
6. PostgreSQL race-test: отдельный добровольный тест двух независимых подключений. Запускается только при явном `AUTOCODEX_TEST_PG_URL` на **изолированную локальную БД** `autoc_test_*`. Никогда не использует штатный `DATABASE_URL`.

## Остаточные риски и границы

- **v0.42 ещё не закрыт целиком:** SQL EXPLAIN и query-count на реальном PostgreSQL нужны также для seller supplier variants, новых ставок/категорий и mixed carts. Тест PG race без специальной тестовой БД пропускается.
- Legacy резервы с некорректным или повторно использованным ключом не могут быть безопасно разморожены автоматически. Нужна отдельная утверждённая ручная инвентаризация и доказательство остатка.
- Финансовая политика min_contribution, ограничение торговой цены и налоговые профили требуют отдельного утверждения: релиз не меняет ставки/фискализацию.
- ROSSKO XLSX «Кратность отгрузки» всё ещё нужно документально подтвердить у поставщика; не меняем смысл молча.
- Автоматический retention worker, скрытые cron-задания и автоудаление не включены.
- Реальные покупки у поставщиков только курьером на заранее подтверждённую точку приёмки, контакты — из неё; новые WRITE не создавались.

## Безопасные команды (PowerShell в одну строку)

После установки / сборки запустить `pytest tests/test_marketplace_completion_v0421.py`, затем всю регрессию `pytest tests`, затем `scripts/release_gate_v0421.py`. Для изучения кандидатов на удаление без каких-либо изменений:

`Set-Location 'C:\Users\bogdan\Desktop\autocodex'; docker compose exec -T web python scripts/snapshot_retention_v0421.py --days 180 --limit 50`

**Никогда не применять `--apply` по результату одной лишь статической проверки.** Перед этим нужно разрешение на обслуживание, резервная копия БД и PostgreSQL интеграционные тесты.
