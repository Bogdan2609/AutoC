# Autocodex v0.35.0 — закупки поставщиков: безопасная сверка и запрос отмены

База установки: **v0.34.0**. Обновление инкрементальное, а не полный проект. Не включайте боевые закупки/платежи только из-за установки ZIP. Обязательная миграция Alembic: `20261026_0036` (последняя, после `20261023_0035`).

## Действительно реализовано

1. `SupplierPurchaseAttempt` имеет состояния `accepted_unverified`, `reconciling`, `verified`, устойчивую метку lease-токена и время сверки; исходный `dispatch_unknown` сохраняется, не снимается автоматическим повтором.
2. ROSSKO `GetCheckout` ACK с ID **не переводит** заказ в `supplier_confirmed`: теперь только `accepted_unverified`. Повторный `/confirm` не создаёт второй запрос на закупку.
3. Административный **read-only** `GetOrders`: проверка конкретных идентификаторов, исходного аккаунта и оплаченной строки, артикула/бренда, суммарного количества, цены `Decimal`, явной валюты `RUB`, комментария с UUID заказа (если возвращён). Отсутствующие заказы в ограниченной выдаче = `pending`, не отказ. Неопределённый результат = ручная проверка, **без** повтора `GetCheckout`.
4. Сверка фиксируется как отдельный lease (один активный запрос, восстановление после 10 минут). Только подтверждённый точный заказ переводит локальные `Procurement` и `SaleLineExecution` в `accepted`/`supplier_confirmed` и фиксирует audit-событие. Наличие в GetOrders не доказывает физическую доставку.
5. Запрос на отмену — административная заявка в DB и audit, **не** внешнее подтверждение отмены: у ROSSKO, ADEO, PARTKOM и Forum настоящий вызов отмены остаётся недоступным до проверки контракта. Повторный запрос идемпотентен.
6. В мониторинге и shadcn админке подсвечиваются `accepted_unverified`, `dispatch_unknown`, `reconciling`. Для администратора появились действия «Сверить GetOrders» и «Запросить отмену (вручную)» с правами доступа и предупреждением.
7. Контакты поставщику берутся только со своего склада/ПВЗ, `PARTS.Part.comment` содержит UUID собственного заказа, поставщикам только **курьерская доставка**, покупатели платят **только СБП**. Эти прежние правила не менялись.

## Матрица поставщиков

| Поставщик | План | Живая отправка | Чтение статуса | Реальная отмена |
| --- | --- | --- | --- | --- |
| ROSSKO | Да | Через существующий защищённый ручной GetCheckout с флагами; не автоматически | Новый GetOrders по подтверждённым IDs | Нет, только ручная заявка |
| ADEO | Да, только план | Нет: нет проверенного контракта статусов | Нет | Нет |
| PARTKOM | Да, `flagTest=1` | Нет, test-only | Нет | Нет |
| Forum-Auto | Да, только план | Нет: `eid` меняет количество, нет безопасности повтора | Нет | Нет |

API `/api/v1/admin/supplier-purchases/capabilities` явно возвращает ограничения. Никакая запись «план создан» не означает внешнюю закупку.

## API администратора

- `GET /api/v1/admin/supplier-purchases/capabilities` — матрица поддерживаемых операций (без секретов).
- `GET /api/v1/admin/supplier-purchases/{uuid}` — оперативное состояние без контактных данных.
- `POST /api/v1/admin/supplier-purchases/{uuid}/reconcile` — одна READ-операция GetOrders, если есть внешний номер, API включён и квота доступна. У `dispatch_unknown` есть двухминутный карантин. Нет ID — только обращение к поддержке поставщика.
- `POST /api/v1/admin/supplier-purchases/{uuid}/request-cancellation` — регистрирует ручную заявку только для `verified`; ничего не отправляет поставщику.

Ошибки SOAP/HTTP заменяются фиксированными кодами; сырой XML и учетные данные не возвращаются клиенту. Доступ защищён существующими правами административных операций закупки.

## Необходимое подтверждение ROSSKO GetOrders

В текущих примерах ответа `GetOrders` **нет гарантированного поля валюты**. По бизнес-правилу RUB-only нельзя утверждать, что любое денежное значение — рубли. Если `parts.part.currency` не равно буквальному `RUB`, автоматическое `verified` блокируется (`unsupported_order_currency`), даже если SKU/количество совпали. В тестах используется фикстура с **явно** указанной валютой RUB. Перед боевой активацией потребуется подтверждённый договорный источник валюты GetOrders и его корректная реализация в адаптере. Не следует добавлять фиктивный `currency: RUB` в ответы.

## Команды PowerShell — по одной строке

После установки ZIP **до включения боевых флагов**:

`Set-Location 'C:\Users\bogdan\Desktop\autocodex'; docker compose up -d --build; docker compose ps`

Просмотр статуса Alembic:

`Set-Location 'C:\Users\bogdan\Desktop\autocodex'; docker compose run --rm migrate alembic current`

Контроль работы backend:

`Set-Location 'C:\Users\bogdan\Desktop\autocodex'; docker compose logs --tail=100 migrate web worker`

Compose сервис `migrate` настроен как обязательная успешная зависимость `web`/`worker`. При ошибке миграции сервисы не должны быть подняты принудительно. Архив содержит только дельту v0.35, без `.env`, ключей и логов.

## Что нельзя объявлять завершённым

- Жизненный цикл реальных заказов ADEO, PARTKOM, Forum (отправка/статусы/отмена) — по-прежнему не реализован; нужны реальные контракты и тестовый сервер/portal-test.
- Проверенная отмена заказа ROSSKO и компенсационная логика поставщика — не реализованы.
- Автоматическая закупка непосредственно после подтверждённого платежа СБП не включена.
- Финальная сверка статусов отправки/доставки у каждого поставщика и гарантия переданных к курьеру товаров — не реализованы.
- Полный тестовый прогон и UI build под Node были недоступны для завершения в данной среде; обязательна проверка на Docker пользователя.
- Миграция проверена как новая Alembic head и по модели, но прогон против реальной PostgreSQL 18.6 в этой среде не выполнен.

## Предварительные проверки

Целевой регрессионный набор: **90 passed** (без внешней сети). Длительный полный тестовый прогон достиг примерно 55% набора без обнаруженного падения, но завершился по лимиту времени (не является полным PASS). Неподтверждённые части не включать в release readiness.
