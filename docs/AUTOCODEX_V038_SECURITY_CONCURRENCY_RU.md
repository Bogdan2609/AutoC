# Autocodex v0.38.0 — безопасность, транзакции и очереди

Дата: 2026-10-26. Тип: инкрементальный ZIP поверх **точной** версии v0.37.0.

## Область изменения

1. `app/core/security.py`: `require_admin()` больше не делает `commit()` записи административного аудита **до** выполнения операции. `flush()` проверяет доступность аудита в той же транзакции. При ошибке сохранения аудита вызывается rollback, изменение не исполняется. Если endpoint завершится исключением без commit, и аудит, и его непроведённые бизнес-изменения откатятся; при успешном commit фиксируются вместе. Для отдельного журнала неуспешных попыток потребуется собственный отдельный security-event log/outbox — это не часть транзакционного business audit.
2. `app/modules/payments/api.py`: при подтверждении YooKassa общий заказ блокируется `SELECT ... FOR UPDATE` **перед** строкой конкретного Payment. Сверка по двум разным платежам одного заказа теперь сериализуется через строку Order. Сверяются неизменность `provider_id`, `order_id`, сумма и валюта. Отмена альтернативного платежа не сбрасывает подтверждённый ранее оплаченный заказ; второй успешный платёж переводится в конфликт/ручную сверку, без повторной закупки. Некорректный ответ провайдера отклоняется кодом 409.
3. `app/workers/runner.py`: строка Refund блокируется при подготовке реального POST; прежнее состояние `uncertain` сохраняется в БД до вызова банка, повтор POST после неопределённого результата не выполняется. Зависший `feed_catalog_sync` теперь **не** перезапускается вслепую: job отправляется в manual_review, синхронизация переводится в `paused` с машинным кодом причины. Автоматический повтор чтения статусов банковских платежей/возвратов остаётся разрешённым и ограниченным.
4. `app/main.py`: ограничение размера потоковых JSON-запросов (POST/PUT/PATCH под `/api/`), включая отсутствие Content-Length: до 1 МиБ, для webhook YooKassa — 16 КиБ, для дорогих поисковых маршрутов — 64 КиБ. Не-JSON upload/multipart не затронуты: ограничения на них необходимы отдельно на ingress и на маршруте.
5. `app/modules/accounts/api.py`: нормализация пользовательского email в register/login через `strip().casefold()`. Администраторские login/email не изменены. Сохраняется текущая session-token authentication, refresh-token механизм не создаётся.
6. `pyproject.toml`, `app/main.py`: версия backend 0.38.0.

## Не изменено

- Режим оплаты: **СБП**, YooKassa; никаких карточных платежей/холдов.
- Валюта: **RUB**, без скрытой конвертации; денежные значения Decimal.
- Закупки у поставщиков: **только курьерская доставка** на заранее настроенный адрес; контакт из склада/ПВЗ, а не из заказа покупателя.
- ROSSKO: comment каждой позиции — UUID нашего заказа. Неизвестное состояние внешней отправки запрещает повтор.
- Не добавлены новые реальные отправки ADEO/PARTKOM/Forum, не включены checkout/payment reconciliation флаги.
- **Новых Alembic-миграций нет.** Миграции предыдущего релиза v0.37 должны быть применены отдельно.

## Тестирование

- Локально Python 3.13: 92 успешно пройденных теста в профильном наборе (включая 10 новых тестов v0.38).
- Полный набор: **699 passed, 1 skipped**, затем первый FAIL `tests/test_unit.py::test_liveness_and_admin_denied_without_token` по причине `ModuleNotFoundError: No module named 'psycopg'`. Такой прогон **не является полным PASS**. Репозиторий требует Python 3.14, а локальные версии Python/пакетов отличаются от зафиксированных в `pyproject.toml`.
- Проверка без внешних сетевых соединений; реальные API не вызывались.
- Конкурентное поведение `SELECT ... FOR UPDATE` на PostgreSQL необходимо испытать с двумя независимыми транзакциями на пользовательском Docker; SQLite не реализует PostgreSQL row locks.

## Оставшиеся технические риски (не скрываются)

- Некоторые административные endpoints имеют **собственные промежуточные commit**. Общий ранний audit commit устранён, но для атомарности всех многошаговых бизнес-операций требуется дальнейший рефакторинг unit-of-work / outbox. Endpoint, который вообще не делает commit, не зафиксирует транзакционный аудит (и не должен считаться совершившим бизнес-изменение).
- Исходный worker использует долгоживущие внешние операции и не имеет lease-fencing token для **всех** видов задач; для каталога принято безопасное решение manual review при timeout, а не автоматическая гонка.
- Не реализованы глобальная блокировка редактирования уже оплаченных строк заказа, refresh-токены, полное верифицированное исполнение API закупок ADEO/PARTKOM/Forum.
- Для загрузки изображений/CSV и multipart лимиты должны задаваться Nginx/ingress и отдельно по назначению маршрута.
- Продакшн webhook YooKassa должен допускаться через защиту сетевого периметра; API re-query является основным механизмом проверки. Не внедрять несуществующую универсальную HMAC подпись.

## Приёмка в Docker / PostgreSQL (до боевого включения)

1. Сделать backup PostgreSQL и директории проекта. Проверить, что исходные SHA-256 совпадают с манифестом ZIP.
2. Выполнить `docker compose up -d --build`, убедиться в успешном `migrate`, `web`, `worker`.
3. Запустить pytest на Python 3.14, включая `tests/test_security_transactions_v038.py` и остальные тесты. Испытать два конкурентных webhook на один заказ и на **два разных** Payment ID.
4. Принудительно оборвать worker на `feed_catalog_sync`, убедиться в переводе в manual_review/paused без повтора материалиации.
5. Выполнить возврат с неопределённым ответом на тестовом шлюзе: единственный внешний POST, затем только сверка/ручная проверка.
6. Проверить rollback административной операции в БД: запись аудита не должна фиксироваться одна при откате операции. Проверить журнал аудита на успешно завершённом write.
7. Проверить нагрузку/ограничения nginx и FastAPI на chunked JSON и отдельные multipart uploads.
8. Не включать боевую закупку/сверку платежей без явного утверждения настроек и реальных API-контрактов.
