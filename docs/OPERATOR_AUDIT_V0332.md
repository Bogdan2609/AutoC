# Autocodex v0.33.2 — аудит административной панели

Исходный код: v0.33.1 (полная поставка). Изменения v0.33.2 ограничены административным чтением, диагностикой, настройкой привязки реквизитов (через уже существующее API) и интерфейсом. Новые бизнес-операции не разрешаются автоматически.

## Подтверждённые недостатки и исправления

| Недостаток | Исправление |
|---|---|
| Статические надписи «v0.31.9» и «СБП/закупки выключены», которые могут расходиться с настройками | В меню и шапке обновлена версия; обзор показывает текущие глобальные переключатели, но не трактует доступные реквизиты как подтверждение финансовой готовности |
| Нет единого экрана проблем и исключений | «Центр контроля»: агрегаты заказов, возвратов, закупок и фоновых заданий; просроченные задания |
| Нет проверки цепочки API-аккаунт → адрес → склад/ПВЗ → получатель | «Готовность приёмки»: сервер проверяет принадлежность точки, включение, верификацию, курьерскую доставку ROSSKO, наличие адреса и корректность контакта тем же валидатором, что и закупка |
| Аккаунты без направлений не видны в проверке логистики | Отдельный список аккаунтов без привязанных адресов поставок |
| Список заказов показывает последние 100 без фильтрации по статусу | Новый защищённый GET с пагинацией и фильтрацией; отдельный режим нескольких статусов ручного контроля |
| Нет истории событий заказа в админке | Ограниченная хронология `OrderWorkflowEvent`, без произвольных evidence, телефонов и адресов |
| Закупочные попытки и задания показывались только в коротких списках | Новые постраничные списки; закупка связывается с UUID заказа, задания не возвращают сырой текст ошибки |
| В модели/сервере есть `external_requisite_id`, но он отсутствует в форме адреса поставки | Отображение, создание и редактирование реквизита; пустое значение допускает определение единственной организации ROSSKO через живой API. Изменение привязки сбрасывает верификацию на сервере |
| Быстрый выбор ROSSKO предлагал самовывоз | Фильтр курьерского способа `000000002` при привязке ROSSKO |

## Реализованные эндпоинты

`GET /api/v1/backoffice/monitor/configuration` — безопасные флаги и состояние среды, без значений секретов.

`GET /api/v1/backoffice/monitor/attention` — агрегаты по статусам и просроченная очередь.

`GET /api/v1/backoffice/monitor/receiving-readiness` — состояние адресов поставок и аккаунтов без адресов (ограниченные выборки).

`GET /api/v1/backoffice/monitor/orders` — пагинация, статус и `review_only`.

`GET /api/v1/backoffice/monitor/orders/{order_id}/events` — до 100 событий, свободные доказательства скрыты.

`GET /api/v1/backoffice/monitor/purchases`, `GET /api/v1/backoffice/monitor/jobs` — защищённые постраничные списки.

Все защищены `Depends(require_admin)` и **не отправляют поставщикам никаких запросов, заказов или платежей**.

## Ограничения и дальнейшие задачи

- Доступ админки пока основан на общем токене, а не на полноценной ролевой модели сотрудников, двухфакторной аутентификации и индивидуальном журнале изменений. Для коллективной эксплуатации это обязательные отдельные задачи.
- Конфигурационная готовность адреса **не подтверждает** актуальные тарифы доставки, доступный остаток, реальный ответ поставщика и статус платежей.
- Для ADEO/PARTKOM/FORUM-AUTO нельзя автоматически использовать идентификатор курьера ROSSKO — контракты разные.
- В платёжных разделах есть симуляционные контуры. Они не должны восприниматься как реальная фискализация или банковская сверка.
- Существующие бизнес-маршруты (публикация, изменение остатков, котировка) не изменены; нового разрешения закупки нет.

## Ручная приёмка

Войти в `/operator` → «Обзор» → «Центр контроля» → «Готовность приёмки» → «Склады и ПВЗ» → «Адреса поставок» → «Заказы» → «Закупки» → «Задания». Убедиться, что состояние конфигурации соответствует `.env`, проверка не показывает имя/телефон получателя, отсутствующая фамилия или телефон делает точку неготовой, а редактирование реквизита сбрасывает подтверждение поставочного направления. Не включать реальные платежи или закупки для проверки этих страниц.
